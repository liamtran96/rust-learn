# Create Rust retrieval homework

Treat the repository root as the base for every path. Interpret text following `$homework`
as an optional focus, question count, or request to review an existing homework file.

## Generate homework

1. Read `topics/rust/progress.md` first. Treat its completed exercises, phase, and week as
   the authoritative boundary for what Liam has learned. Do not test later material merely
   because it appears in the study plan or notes.
2. Read `topics/rust/journal.md`, then read all topic journals it lists under
   `topics/rust/journal/`. Emphasize substantive questions, confusion, follow-up
   questions, and concepts that needed correction.
3. Read every `topics/rust/<NN-chapter>/mistakes.md` relevant to completed material.
   Prioritize mistakes in this order:
   1. fresh mistakes that were repeated or still felt difficult;
   2. other fresh mistakes;
   3. mistakes reviewed once;
   4. resolved mistakes, only for occasional spaced review.
4. When useful, inspect completed crates under `code/` to make prompts concrete. Do not
   change exercise code or learning records while generating homework.
5. Respect an explicit focus or question count. Otherwise create six questions for roughly
   25-35 minutes:
   - two recall or explain-in-your-own-words questions;
   - two predict, trace, or diagnose questions using short Rust snippets;
   - one small code-writing question;
   - one transfer question that applies a learned rule in a new situation.
6. Mix at least three learned concepts when the records support it. Weight weak concepts
   more heavily than already-solid ones. Change names, values, and scenarios instead of
   copying prior exercises or mistake examples verbatim.
7. Ask for reasoning, not only final output. Keep each prompt independently answerable.
   Do not include solutions, leading hints, answer keys, or links to the exact source note
   before Liam attempts the work.
8. Create `topics/rust/homework/` if absent. Save the set as
   `topics/rust/homework/YYYY-MM-DD-retrieval-<focus>.md`, using `mixed` when there is no
   focus. Never overwrite a file; append `-02`, `-03`, and so on when needed.
9. Use this file shape:

   ```markdown
   # Rust Retrieval Homework - YYYY-MM-DD

   **Focus:** <concepts>
   **Based on:** completed material through <phase/week from progress.md>
   **Timebox:** <estimate>

   ## Instructions
   Answer from memory first. For code questions, predict before running anything. Explain
   the Rust rule behind each answer. Write answers directly below each prompt.

   ## Questions

   ### 1. <short title>
   <prompt>

   **Your answer:**

   <!-- Repeat for every question. -->

   ## Confidence check
   For each question, rate confidence from 1 (guessing) to 5 (certain) before checking notes.
   ```

10. Before replying, verify every tested concept appears in completed progress, a prior
    journal entry, a relevant mistake log, or completed exercise code.
11. Reply with the created path, question count, timebox, and the two or three concepts
    emphasized. Invite Liam to fill in the file and ask for a review.

### Automatic chapter closeout

When called by the journal workflow after a chapter changes from incomplete to complete:

1. Use that chapter as the explicit focus and draw questions only from material completed
   in that chapter, while still using earlier learned concepts when a question requires
   them.
2. Generate exactly one homework file for that completion event. Before generating, check
   whether the current journal closeout already created a chapter-focused file; reuse it
   instead of creating a numbered duplicate.
3. Create the homework after progress, journals, and mistake logs have been updated, so the
   completed chapter boundary and newest mistakes are included.
4. Return the created or reused path to the journal workflow so it can include the homework
   in the same focused closeout commit.

## Review submitted homework

1. Read the generated homework, Liam's answers, and the source learning records used by
   each question.
2. Mark each answer `correct`, `partly correct`, or `retry` and explain the governing Rust
   rule concisely. Distinguish syntax mistakes from conceptual mistakes.
3. For `retry`, ask one narrower follow-up before giving the full answer. Follow the
   repository teaching approach and do not write a complete solution unless Liam asks.
   After an entire numbered question is marked correct, always provide a concise,
   canonical **Reference answer** that fully answers the original prompt. Show it only
   after the learner has completed the question, never during a retry. When answers are
   being tracked in the homework file, save the same reference answer beneath that
   question without replacing the learner's attempts.
4. When answers are tracked in the homework file, keep all attempts and review statuses
   for the current numbered question uncommitted. After the entire question is correct and
   its reference answer is saved, create one focused commit containing that question's
   accumulated review. Never commit each retry separately, and leave unrelated changes
   unstaged.
5. End with one focused review recommendation and name the relevant repository note only
   after the attempt has been assessed.
6. Do not update progress, journal, roadmap, or mistake logs merely for generating or
   grading homework. If Liam completes the review and asks to record the session, use the
   `$journal` workflow.
